Conceito

O banco do Supabase é PostgreSQL

MySQLPostgreSQL
Tipobanco relacional, com SQLbanco relacional, com SQL
Driver em Pythonmysql-connector-pythonpsycopg2-binary

O SQLAlchemy gera o SQL para cada banco. Vamos conferir se o projeto tem algum trecho específico de MySQL antes de trocar a conexão.

Mão na massa · passo 1 de 8

Criar o projeto no Supabase

  1. Abrir supabase.com e entrar com a conta do GitHub. O plano grátis não pede cartão.
  2. Criar um projeto novo, com a região South America (São Paulo).
  3. Definir uma senha longa e única. Com símbolos, pedir orientação para codificá-los na URL.
  4. Guardar a senha em local privado. Não enviar na conversa com a IA.
  5. Aguardar o painel mostrar o projeto pronto.

Conceito

Qual endereço de conexão usar

No botão ConnectPortaServe para
Direct connection5432redes com IPv6. Muitas redes não têm
Session pooler5432servidor ligado o tempo todo, em IPv4
Transaction pooler6543função sem servidor, como a da Vercel

O pooler reaproveita conexões com o banco. Nesta aula, usar o Transaction pooler para a API na Vercel.

Mão na massa · passo 2 de 8

Trocar o banco no .env

backend/.env · o formato da linha do banco
URL_DO_BANCO=postgresql://postgres.REF:SENHA@HOST:6543/postgres
  1. No Supabase, clicar em Connect e copiar a URI do Transaction pooler.
  2. Substituir [YOUR-PASSWORD] pela senha do passo 1. Codificar os símbolos para uso na URL, se houver.
  3. No backend/.env, comentar a linha antiga do MySQL com # e colar a nova.
  4. Conferir que o .env continua no .gitignore. Essa linha tem senha.

Mão na massa · passo 3 de 8

Instalar o driver e ajustar o banco.py

exemplo do professor · backend/banco.py, só o que muda
from sqlalchemy.pool import NullPool

# não manter um pool de conexões no SQLAlchemy;
# o pooler do Supabase faz esse trabalho
engine = create_engine(configuracao.url_do_banco, poolclass=NullPool)
  1. No terminal do backend/, com o venv ativo, executar pip install psycopg2-binary.
  2. Executar pip freeze > requirements.txt de novo.
  3. No banco.py, acrescentar o import e o poolclass=NullPool.

Mão na massa · passo 4 de 8

Criar as tabelas no Supabase

terminal · dentro de backend/, com o venv ativo
python criar_tabelas.py
alembic stamp head
  1. Executar python criar_tabelas.py. Se terminar sem erro, executar alembic stamp head.
  2. No Supabase, abrir o Table Editor. As tabelas do projeto e a alembic_version aparecem lá.
  3. Executar fastapi dev main.py, cadastrar cada perfil no /docs e entrar com cada um.

Segurança

Ativar o RLS nas tabelas

O Supabase tem uma API de dados própria. Vamos ativar o RLS para restringir o acesso às linhas das tabelas por ela.

  1. No Table Editor, abrir cada tabela do projeto.
  2. Clicar em Enable RLS e confirmar. Sem políticas, os acessos com papéis comuns dessa API ficam bloqueados.
  3. Testar o login de novo. A conexão com o usuário postgres passa por fora do RLS. O controle de acesso continua na API de vocês.

A API tem endereço próprio. O projeto da tela encaminha os pedidos de /api para ela. O navegador acessa uma origem só.

Mão na massa · passo 5 de 8

Publicar a API

  1. Conferir se o .env ficou fora do Git antes de fazer commit e push do backend.
  2. Em vercel.com, entrar com o GitHub. Importar o repositório em Add New Project.
  3. Em Root Directory, escolher backend. Em Environment Variables, cadastrar URL_DO_BANCO e CHAVE_DO_TOKEN.
  4. Clicar em Deploy e aguardar.
  5. Abrir https://NOME-DA-API.vercel.app/health. Tem que aparecer {"status":"ok"}.

Leitura linha a linha

O vercel.json encaminha o /api

exemplo do professor · frontend/vercel.json
{
  "rewrites": [
    {
      "source": "/api/:caminho*",
      "destination": "https://tarefa-certa-api.vercel.app/:caminho*"
    }
  ]
}
  1. O source pega todo pedido que começa com /api/ e guarda o resto em :caminho*.
  2. O destination manda esse resto para a API, sem o /api. É o handle_path da aula 2.

Mão na massa · passo 6 de 8

Publicar a tela

  1. Criar o frontend/vercel.json com o endereço da API do passo 5. Fazer commit e push.
  2. Na Vercel, em Add New Project, importar o mesmo repositório de novo.
  3. Em Root Directory, escolher frontend. A Vercel reconhece o Vite sozinha.
  4. Clicar em Deploy e abrir o endereço .vercel.app da tela.
  5. Entrar com cada perfil. Na aba Rede, os pedidos vão para /api/... no mesmo endereço.

Conceito

A API agora é uma função

Execução sob demandaA plataforma inicia a função quando necessário. A primeira resposta pode demorar mais.
Sem disco persistenteNão contar com arquivos locais entre execuções. Nesta aula, os dados ficam no banco.
Logs no painelO que a API escreveria no terminal aparece em Logs, no projeto da Vercel.

Com NullPool, o SQLAlchemy não mantém conexões ociosas. O pooler do Supabase reaproveita as conexões com o banco.

Mão na massa · passo 7 de 8

Configurar o subdomínio

  1. No projeto da tela, abrir Settings e depois Domains.
  2. Adicionar o subdomínio que o professor entregou.
  3. Copiar o registro que a Vercel mostra, com tipo, nome e valor, e mandar ao professor.
  4. Aguardar a validação do domínio e a emissão do certificado pela Vercel.
  5. Abrir o subdomínio com https://. Conferir o certificado no navegador e testar o login.

Mão na massa · passo 8 de 8

Testar o deploy pelo Git

  1. Mudar um texto da tela no frontend/.
  2. Fazer commit e push na main.
  3. Abrir a aba Deployments do projeto da tela. Um deploy novo começa sozinho.
  4. Recarregar o subdomínio quando o deploy terminar. O texto novo aparece.
Com a integração padrão, um push na branch de produção inicia um deploy. Quando ele passa, a Vercel atualiza o site. Outras branches geram prévias.

Recapitulando

O que vocês fizeram hoje

  • Na troca de banco, ajustamos URL, driver e pool. Código específico de MySQL precisa ser conferido.
  • Escolhemos o Transaction pooler para as conexões da API na Vercel.
  • Na Vercel, o vercel.json encaminha o /api, como o Caddy fazia.
  • Senha mora nas variáveis da plataforma, nunca no repositório.
  • A integração com o Git inicia o deploy após o push na branch de produção.
