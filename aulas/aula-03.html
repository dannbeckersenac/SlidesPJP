A dor de hoje

Um pedido que não deveria existir

requisição que a API de ontem aceita sem reclamar
POST /pedidos
{
  "cliente": "",
  "item_id": "pizza",
  "quantidade": -3,
  "observacao": "..."
}
Cliente sem nome. Item que não é número. Quantidade negativa, ou seja, o restaurante vai dever pizza para o cliente. E a sua API respondeu 200 OK.

A tentativa óbvia

Validar na mão

backend/rotas/pedidos.py
@router.post("")
async def criar_pedido(request: Request):
    dados = await request.json()

    if "cliente" not in dados or not dados["cliente"].strip():
        raise HTTPException(400, "cliente é obrigatório")
    if not isinstance(dados.get("item_id"), int):
        raise HTTPException(400, "item_id precisa ser número")
    # ... e ainda faltam quantidade, observação, tipo do preço
Funciona, e é insustentável: doze linhas para três campos, repetidas em cada rota.

A virada

Descrever em vez de conferir

Conferindo campo a campo
if "cliente" not in dados:
    raise ...
if not dados["cliente"].strip():
    raise ...
if not isinstance(
    dados["quantidade"], int):
    raise ...
if dados["quantidade"] <= 0:
    raise ...
Declarando como o dado é
class PedidoCriar(BaseModel):
    cliente: str = Field(min_length=2)
    item_id: int
    quantidade: int = Field(gt=0)
    observacao: str | None = None

Quatro linhas descrevem o que doze linhas conferiam, e a segunda versão ainda aparece no /docs.

Conceito

Pydantic: o formato como código

Um BaseModel é uma classe que descreve o formato de um dado. O FastAPI usa essa descrição para três coisas ao mesmo tempo, sem você pedir:

1
ConverteTransforma o JSON que chegou em objeto Python já tipado.
2
ValidaRecusa o que não bate com a descrição, antes da sua função rodar.
3
DocumentaPublica o formato exato no /docs, campo por campo.
Ideia central: descreva o dado uma vez e ganhe validação, conversão e documentação.

Mão na massa · passo 1 de 4

A rota que ficou honesta

backend/rotas/pedidos.py
@router.post("", status_code=201)
def criar_pedido(pedido: PedidoCriar):
    novo = {"id": len(pedidos) + 1, **pedido.model_dump()}
    pedidos.append(novo)
    return novo
  1. Crie a pasta backend/esquemas/ e escreva a classe PedidoCriar herdando de BaseModel.
  2. Na rota, troque o Request pelo tipo do modelo: pedido: PedidoCriar. Toda a validação virou essa anotação.
  3. Apague as doze linhas de if. Dentro da função, pedido.quantidade já é um inteiro maior que zero, garantido.
  4. Acrescente status_code=201 no decorador para comunicar que algo foi criado.

  3. Leia a resposta: status 422, dizendo qual campo falhou e por quê. É disso que o React precisa para pintar de vermelho o campo certo.

Boa prática

O que entra não é o que sai

CampoEntrada / Saída
cliente, item_id, quantidadeo cliente envia, e volta na resposta
idsó sai, porque quem gera é o servidor
criado_em, statussó sai, porque o cliente não escolhe
observacao_internanunca sai, é da cozinha
Usar o mesmo modelo para entrada e saída é como deixar um cliente definir o próprio id ou ver dado interno do restaurante. Na aula 13 isso vira falha de segurança de verdade.

Mão na massa · passo 3 de 4

Dois modelos, um por direção

O que o cliente manda
class PedidoCriar(BaseModel):
    cliente: str = Field(min_length=2)
    item_id: int
    quantidade: int = Field(gt=0)
O que a API devolve
class PedidoSaida(BaseModel):
    id: int
    cliente: str
    total: float
  1. Escreva as duas classes em backend/esquemas/pedido.py.
  2. Repare no id e no total: quem gera os dois é o servidor, não o cliente.
  3. Declare a saída no decorador, com response_model=PedidoSaida.
  4. Confira o /docs: os dois formatos aparecem separados agora.

O obstáculo final

"Mas no /docs funcionava!"

Você aponta o React para a sua API e o console mostra um erro que não fala de pedido nenhum:

console do navegador
Access to fetch at 'http://127.0.0.1:8000/itens' from origin
'http://localhost:5173' has been blocked by CORS policy

A API está certa. O navegador é que bloqueia por padrão uma página de um endereço pedindo dados de outro. É proteção, não defeito. O servidor precisa autorizar explicitamente.

Mão na massa · passo 4 de 4

Autorizando o seu front

backend/main.py · from fastapi.middleware.cors import CORSMiddleware
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],
    allow_methods=["*"], allow_headers=["*"],
)
  1. Descubra o endereço exato do seu front. O npm run dev imprime ele no terminal.
  2. Registre o middleware no main.py com só esse endereço em allow_origins.
  3. Recarregue o React. O erro do console some e a lista aparece na tela.
Nunca allow_origins=["*"]: isso libera a sua API para o mundo inteiro.

Recapitulando

O que fica da aula 3

  • Validar na mão funciona e não escala. Fora que nem aparece na documentação.
  • Um BaseModel descreve o dado uma vez e entrega conversão, validação e documentação juntas.
  • O 422 diz qual campo falhou e por quê. É o que o formulário precisa.
  • Entrada e saída são modelos diferentes. O cliente não define id nem vê dado interno.
  • O CORS é proteção do navegador. Autorize o seu front, nunca o mundo inteiro.
