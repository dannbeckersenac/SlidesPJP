Conceito

Migration: o commit do banco

O Git guarda cada mudança do código. A migration guarda cada mudança das tabelas, em ordem.

1
O arquivoUm .py por mudança, em migracoes/versions/. Vai para o Git.
2
A versãoUma tabela alembic_version diz em que mudança o banco está.
3
O upgradeRoda só as mudanças que o banco ainda não tem.

Quem faz isso é o Alembic, escrito pelo mesmo autor do SQLAlchemy. Ele compara os modelos com o banco e escreve a mudança.

Conceito

Como o Alembic descobre o que mudou

Lê os modelosPela Base.metadata, o mesmo desenho que o create_all usa.
→
Olha o bancoPergunta ao MySQL que tabelas, colunas e chaves existem.
→
Escreve a diferençaUm arquivo com o que falta. Você lê antes de aplicar.

O nome disso é autogenerate. Ele acerta tabela, coluna e chave. Não confie nele para trocar nome de coluna: ele lê como apagar uma e criar outra.

Depois do intervalo

Segundo tempo

A regra da cartilha recusa. Hoje ela passa a dizer por quê, e a API passa a contar isso para quem usa.

A dor do segundo tempo

Dois motivos para recusar, um None só

  1. No /docs do exemplo, abro uma tarefa com solicitante_id 99, que não existe. Volta 422, Solicitante inválido.
  2. Abro outra com o 2, que existe mas é executor. Volta a mesma mensagem.
  3. Apago o if resultado is None da rota e repito. Volta 500.
O None não diz o motivo. E a rota que esquece de testar ele quebra.

Onde paramos

O serviço recusa sem explicar

Python que faltava

try e except: tentar, e saber o que fazer se der erro

no terminal, com python
try:
    int("abc")                    # isto levanta um ValueError
except ValueError as erro:          # pega só esse tipo de erro
    print("Não deu:", erro)          # e o programa segue, sem quebrar
  1. No terminal, digite python, cole o código e aperte Enter duas vezes.
  2. Aparece Não deu: invalid literal for int(), e não o erro vermelho de sempre.

O raise você já usa desde a aula 2, com o HTTPException. O except é o outro lado: quem pega.

Python que faltava

Uma exceção com o nome da sua regra

→

→

Leitura linha a linha

Cada recusa com o seu motivo

exemplo do professor · backend/servicos/tarefa.py
from servicos.excecoes import SolicitanteInvalido

def criar(sessao, tarefa: TarefaCriar):
    solicitante = repositorio_usuario.buscar_por_id(sessao, tarefa.solicitante_id)
    if solicitante is None:                           # motivo 1
        raise SolicitanteInvalido("Não existe usuário com esse id")
    if solicitante.tipo != "solicitante":             # motivo 2
        raise SolicitanteInvalido("Só quem é solicitante pode abrir tarefa")
    return repositorio.salvar(sessao, {"situacao": "aberta", "itens_feitos": 0,
                                       **tarefa.model_dump()})

O raise para a função ali mesmo. Nada depois dele roda, e nada é gravado.

Leitura linha a linha

A regra ganha nome próprio

exemplo do professor · backend/servicos/item.py
def aplicar_item(tarefa, tipo):                 # a regra da cartilha, e só ela
    if tarefa.situacao == "concluida":
        raise TarefaConcluida("A tarefa já foi concluída e não aceita item novo")
    if tipo == "etapa":
        tarefa.itens_feitos += 1
        tarefa.situacao = "em andamento"
    else:
        tarefa.situacao = "concluida"
def lancar(sessao, tarefa, item):
    aplicar_item(tarefa, item.tipo)                  # se recusar, nada abaixo roda
    return repositorio.salvar(sessao, {"tarefa_id": tarefa.id, "data": date.today(),
                                       **item.model_dump()})

Segundo tempo · passo 2 de 4

O serviço levanta, não devolve None

  1. No serviço da regra, importe as exceções de servicos.excecoes.
  2. Troque cada return None de recusa por raise com a exceção do motivo e uma frase para a tela.
  3. Leve a regra para uma função com o nome dela, como o aplicar_item, e chame essa função no lugar do bloco.
  4. Confira que o serviço não importa HTTPException nem escreve número de status.
O return None de quando não encontrou continua. Não achar não é recusa, e o 404 já tem a sua dependência.

O atalho

Traduzir uma vez, no main.py

backend/main.py · depois do app = FastAPI()
from fastapi.responses import JSONResponse
from servicos.excecoes import TarefaConcluida

@app.exception_handler(TarefaConcluida)       # vale para todas as rotas
def tratar_tarefa_concluida(requisicao, erro):
    return JSONResponse(status_code=409, content={"detail": str(erro)})
Com ele, a rota não precisa de try. As duas formas funcionam: entregue a que você sabe explicar.

A IA costuma escrever este. Quando a mesma exceção aparece em várias rotas, ele evita repetir o except.

Recapitulando

O que fica da aula 7

  • O create_all não altera tabela. A migration guarda cada mudança do banco, em ordem.
  • O Alembic compara os modelos com o banco e escreve a diferença. Você lê antes do upgrade.
  • A regra mora numa função com nome. Cada recusa é uma exceção, com o motivo no nome.
  • O serviço fala de negócio, a rota fala HTTP: o except escolhe o status.
  • A IA rascunha a documentação. Você prova cada linha no /docs antes de entregar.
